# Admin Web — Дизайн ТЗ (Shyraq)

**Аудитория:** UX/UI-дизайнер.
**Цель:** полное техническое задание на дизайн **всех** экранов Admin Web. Из этого документа можно отрисовать весь интерфейс администратора садика, не зная backend.

**Парный документ:** [`ADMIN_FRONTEND_HANDOFF.md`](ADMIN_FRONTEND_HANDOFF.md) — функциональные контракты (данные/эндпоинты). Этот файл — про экраны, состояния, поведение, визуал.

**Контекст продукта:** Shyraq — SaaS для управления частными детскими садами в Казахстане. Admin Web — рабочий кабинет администратора **одного садика**. Это операционный, насыщенный данными интерфейс ежедневного использования (как CRM/админка), не маркетинговый сайт.

---

## 1. Пользователь и контекст использования

**Персона:** администратор / заведующая / управляющий частного детского сада. Возраст 25–55, **не технический**. Работает с компьютера в кабинете садика, часто параллельно с телефонными звонками родителей. Заходит ежедневно, по многу раз. Ценит скорость, ясность, отсутствие двусмысленности при необратимых действиях (архив ребёнка, отмена счёта, отмена скидки).

**Ключевые сценарии (по частоте):**

1. Утро: посмотреть дашборд, посещаемость, новые заявки/лиды.
2. Обработка лида → создание карточки ребёнка → проверка первого счёта.
3. Ответы на заявки родителей (принять/отклонить, переписка).
4. Биллинг: проверить просрочки, отметить оплату наличными, оформить возврат.
5. Контент: опубликовать новость/меню/расписание.
6. Управление детьми/группами/сотрудниками (реже, но критично).

**Среда:** desktop-first (1280–1920px), браузеры Chrome/Safari/Edge актуальные. Должна корректно работать на ноутбуке 1366×768. **Mobile/tablet (<1024px)** — адаптивный mobile shell (33 экрана), см. **§10**. **Desktop (>=1024px)** — sidebar/topbar shell. Для родителей/сотрудников есть отдельные нативные приложения.

**Языки интерфейса:** Русский и Казахский (переключатель в шапке). Весь UI и контент мультиязычны. Часть пользовательских данных вводится на двух языках (название блюда, заголовок новости, название праздника/скидки) — формы должны иметь парные поля RU/KK.

## 2. Общие принципы дизайна

- **Информационная плотность** выше средней — это рабочий инструмент, не лендинг. Таблицы, фильтры, табы — основа.
- **Ясность статусов.** Множество сущностей имеют жизненный цикл (ребёнок, лид, счёт, платёж, возврат, скидка, контент, заявка). Каждый статус — цветной бейдж с устойчивой семантикой цвета (см. §4.6).
- **Защита от ошибок.** Необратимые/денежные действия — модал-подтверждение с явным описанием последствий и (где есть) обязательным полем причины.
- **Скорость.** Списки с фильтрами/поиском/пагинацией; быстрые действия из строки таблицы; минимум кликов до частых операций.
- **Доверие и забота.** Продукт про детей — тёплая, спокойная палитра, дружелюбные иллюстрации в пустых состояниях, без агрессии. Но без инфантильности: это деловой инструмент.
- **Консистентность.** Один паттерн таблицы, формы, модала, фильтра, тоста — переиспользуется везде. Дизайн-система обязательна.

## 3. Глобальный каркас (App Shell)

Единый каркас для всех страниц после входа:

```
┌────────────────────────────────────────────────────────────────┐
│ TOPBAR: [Логотип Shyraq] [Название садика]      [🔔][RU/KK][👤▾] │
├──────────┬─────────────────────────────────────────────────────┤
│ SIDEBAR  │  BREADCRUMBS / Page title + primary action button     │
│ (nav)    │  ───────────────────────────────────────────────────  │
│          │                                                       │
│ группы   │  PAGE CONTENT (таблица / форма / детальная / дашборд)  │
│ разделов │                                                       │
│          │                                                       │
└──────────┴─────────────────────────────────────────────────────┘
```

- **Topbar (фикс.):** логотип + название текущего садика (важно — админ может быть в нескольких садиках; всегда видно, в каком он сейчас). Справа: колокол уведомлений (бейдж непрочитанных), переключатель языка RU/KK, меню пользователя (имя, аватар → Профиль, Мой QR, Выход; если есть другие садики — «Сменить садик»).
- **Sidebar (фикс., сворачиваемый в иконки):** сгруппированная навигация (см. §5). Активный пункт подсвечен. Группы сворачиваемы.
- **Контент-зона:** breadcrumbs (где есть вложенность) + заголовок страницы + основная кнопка действия (например, «Создать карточку») в правом верхнем углу контента.
- **Toasts:** правый нижний угол, авто-скрытие; success/info/warning/error. Реал-тайм события (новая заявка, оплата) — ненавязчивый тост + обновление бейджей.
- **Глобальные состояния:** скелетон-лоадеры при загрузке таблиц/карточек; баннер «нет связи»/«сессия истекла → войдите снова»; экран 403 «нет доступа к разделу».

## 4. Дизайн-система (обязательный набор компонентов)

Спроектировать как переиспользуемую библиотеку:

### 4.1 Типографика

- Шрифт с поддержкой кириллицы и казахских символов (ә, і, ң, ғ, ү, ұ, қ, ө, һ). Например, Inter / Manrope / SF-подобный.
- Иерархия: H1 (заголовок страницы), H2 (секции/табы), H3 (карточки), Body, Caption, Label, Mono (для UUID/токенов/сумм при необходимости).

### 4.2 Сетка и отступы

- Базовая 8px-сетка. Контейнер контента max-width ~1440px, центрирован, с отступами. Таблицы — на всю ширину.

### 4.3 Цвет

- Нейтральная база (фон, поверхности, бордеры, текст 3–4 оттенка).
- Брендовый акцент (1 основной + hover/active). Тёплый, доверительный (зелёный/бирюзовый/мягкий синий — на выбор дизайнера, обосновать).
- Семантика: success (зелёный), warning (янтарный), danger (красный), info (синий), neutral (серый). Используется в бейджах, тостах, кнопках, валидации.

### 4.4 Компоненты (минимальный набор)

- **Кнопки:** primary, secondary, ghost, danger, icon-button; размеры; loading-состояние; disabled с тултипом-причиной.
- **Поля ввода:** text, textarea, number, select (single/multi), combobox с поиском (для выбора ребёнка/группы/сотрудника), date-picker, datetime-picker, time-picker, phone (E.164 маска `+7...`), toggle/switch, checkbox, radio, file-upload (drag&drop + прогресс), парное RU/KK-поле (две вкладки или два инпута).
- **Таблица (DataTable):** колонки, сортировка, фильтр-панель, поиск, пагинация (offset: «1–20 из N» + страницы; cursor: «Загрузить ещё»/«Дальше» — без номеров страниц), row-actions (контекстное меню/иконки), bulk-selection (где нужно), пустое/загрузка/ошибка состояния, sticky-заголовок.
- **Карточка детальная с табами** (паттерн для ребёнка/группы/сотрудника/счёта/заявки): шапка (название + статус-бейдж + основные действия) + табы + контент таба.
- **Модалы:** форма-модал (создать/редактировать), confirm-модал (обычный / destructive с обязательным полем причины), info-модал.
- **Бейджи статусов** (§4.6), **чипы** (фильтры/теги), **тултипы**, **поповеры**, **тосты**, **баннеры/алерты** (info/warning внутри страницы), **пустые состояния** (иллюстрация + текст + CTA), **скелетоны**, **breadcrumbs**, **табы**, **степпер/wizard** (для конструкторов: скидка, диагностическая форма), **календарь/неделя** (расписание, меню), **kanban-доска** (лиды), **KPI-карточка** (дашборд), **донат/бар-чарт** (дашборд), **OTP-инпут** (6 ячеек, для входа и подтверждений).

### 4.5 Состояния каждого экрана (обязательно проектировать все)

Для **каждой** страницы/виджета: **Loading** (скелетон), **Empty** (нет данных + объясняющий текст + CTA создать), **Error** (не загрузилось + кнопка «повторить»), **Success/Filled** (данные есть), **No-access/403** (нет прав), **Filtered-empty** (фильтры ничего не нашли — отдельно от Empty).

### 4.6 Семантика статус-бейджей (единые цвета во всём приложении)

| Сущность                           | Статусы → цвет                                                                                                                          |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Ребёнок (`child_status`)           | card_created (neutral/синий «новый») · active (success) · archived (серый/приглушённый)                                                 |
| Лид (`enrollment_status`)          | new (info) · in_processing (warning) · waitlist (янтарный) · card_created (success) · cancelled (серый) · archive (серый)               |
| Счёт (`invoice`)                   | pending (neutral) · partial (warning) · paid (success) · overdue (danger) · refunded (info) · cancelled (серый)                         |
| Платёж (`payment`)                 | initiated (neutral) · processing (info) · completed (success) · failed (danger) · refunded (info)                                       |
| Возврат (`refund`)                 | pending (warning) · approved (info) · processed (success) · rejected (danger)                                                           |
| Скидка (`custom_discount`)         | draft (neutral) · active (success) · paused (warning) · expired (серый) · cancelled (серый)                                             |
| Контент (`content_status`)         | draft (neutral) · scheduled (info) · published (success)                                                                                |
| Заявка родителя (`parent_request`) | pending (warning) · accepted (success) · rejected (danger) · cancelled (серый)                                                          |
| Сотрудник                          | active (success) · inactive (серый)                                                                                                     |
| Группа/Локация/Камера              | активна (success) · неактивна (серый)                                                                                                   |
| Дневной статус ребёнка             | present (success) · late (warning) · sick (info) · early_pickup (info) · on_vacation (нейтральный) · absent (серый/danger по контексту) |

Бейдж = цвет фона/текста + читаемая локализованная подпись (не «card_created», а «Карточка создана»).

## 6. Постраничное ТЗ

Для каждой страницы: **Назначение** · **Layout** · **Данные/поля** · **Действия** · **Состояния/edge** · **Особые требования**.

### 6.0 Вход (`/login`)

- **Назначение:** аутентификация по телефону + SMS-код.
- **Layout:** центрированная карточка на нейтральном фоне (бренд-иллюстрация/паттерн с темой детства, спокойная). Логотип Shyraq.
- **Шаги (wizard в одной карточке):**
  1. **Телефон:** поле телефона с маской `+7 ___ ___ __ __`, кнопка «Получить код». Подсказка про SMS.
  2. **OTP:** 6-ячеечный OTP-инпут, авто-фокус/переход между ячейками, таймер «Отправить повторно через 0:60», ссылка «Изменить номер». Кнопка «Войти».
  3. **Выбор садика** (только если у пользователя несколько садиков/ролей): список садиков (название + slug), радио/карточки, кнопка «Продолжить».
- **Состояния/ошибки:** неверный код (inline под OTP, счётчик попыток скрыт, но после 3 — экран «номер заблокирован на 15 минут» с таймером), код истёк, лимит запросов (429 — таймер), «нет доступа к админке» (если у пользователя нет admin-роли — дружелюбный экран «Этот аккаунт не администратор садика»).
- **Особое:** не показывать технических кодов ошибок; человеческие формулировки RU/KK. Переключатель языка доступен и на экране входа.

---

### 6.1 Дашборд (`/`)

- **Назначение:** утренний обзор садика; точка входа в работу.
- **Layout:** сетка виджетов.
  - **Ряд KPI-карточек:** Активных детей · Лидов в обработке · Активных сотрудников · Активных групп. Каждая — число + подпись + клик ведёт в раздел.
  - **Посещаемость сегодня:** донат-чарт «В саду / Ушли домой / Отсутствуют / В отпуске / Болеют» + легенда с числами. Фильтр по группе (селект).
  - **Финансы:** карточка «Просрочено» (кол-во + сумма, danger-акцент, клик → счета с фильтром overdue) · «Выручка за месяц (MTD)» · «Выручка за год (YTD)».
  - **Обзор оплат за период:** выбор периода (from/to), 4 показателя (Оплачено/Ожидает/Просрочено/Возвращено — count + сумма) + разбивка по платёжным провайдерам (мини-таблица или бар).
- **Состояния:** скелетоны на каждый виджет независимо; пустые числа (0) — валидное состояние, не error.
- **Особое:** суммы в KZT (формат `120 000 ₸`), даты в таймзоне садика.

---

### 6.2 Лиды / Зачисление (`/enrollments`, `/enrollments/:id`)

- **Назначение:** воронка зачисления от заявки до карточки ребёнка.
- **Список — Layout:** предпочтительно **kanban-доска** по статусам-колонкам: `Новая заявка` → `В обработке` → `Лист ожидания` → `Создана карточка` → `Отменён` → `Архив`. Карточка лида в колонке: имя контакта, телефон, ФИО ребёнка, источник, ответственный (аватар), дата смены статуса. Альтернативный вид — таблица с фильтром по статусу + поиск по телефону/ФИО. Кнопка «Создать лид».
- **Карточка лида (`/enrollments/:id`) — Layout:** двухколоночная: слева данные, справа лог статусов (таймлайн `from→to`, кто, комментарий, когда).
  - **Данные контакта/ребёнка (форма):** ФИО ребёнка*, возраст/дата рождения*, основной законный представитель — ФИО*, телефон* (E.164), связь с ребёнком\*; источник, заметки; выбор группы.
  - **Действия:** смена статуса (кнопки/дропдаун строго по разрешённым переходам state machine — недопустимые задизейблены с тултипом-объяснением), «Назначить ответственного» (селект сотрудника). При переводе в «Создана карточка» — модал-подтверждение с пояснением «будет создан ребёнок, primary-опекун и первый счёт» → после успеха success-баннер со ссылкой на созданную карточку ребёнка.
- **Состояния/edge:** «Лист ожидания» — визуально отдельная колонка/тег «нет мест». Пустая воронка — пустое состояние с CTA «Создать первый лид». Создать карточку ребёнка можно и напрямую (см. 6.3) — упомянуть кнопку-ссылку.

---

### 6.3 Дети (`/children`, `/children/new`, `/children/:id`)

- **Список — Layout:** таблица. Колонки: Фото (мини-аватар), ФИО, ИИН, Группа, Статус-бейдж, Дата зачисления. Фильтры: статус (card_created/active/archived), группа, поиск по ФИО/ИИН. Кнопка «Создать карточку». Архивные — приглушены / фильтр «показать архив».
- **Создание (`/children/new`) — форма:** ФИО*, ИИН (12 цифр, опц. — карточка может быть до получения ИИН), дата рождения*, пол, фото (drag&drop, загрузка через presigned), группа, мед.заметки, аллергии. Подсказка: для перевода из другого садика/офлайн-договора.
- **Карточка ребёнка (`/children/:id`) — Layout:** шапка (фото + ФИО + статус-бейдж + кнопки: **Перевести в группу**, **Архивировать**/**Реактивировать**) + табы:
  1. **Профиль** — все поля, режим просмотр/редактирование.
  2. **Опекуны** — таблица: ФИО, телефон, роль (primary/secondary/nanny), статус (`pending_approval`/approved/rejected/revoked — бейдж), can*pickup (✓/✗), право одобрения (has_approval_rights ✓/✗). Действия: «Добавить опекуна» (модал — **приглашение существующего пользователя**: телефон E.164 **или** user_id, роль, can_pickup; поля свободного ввода ФИО нет — имя резолвится из аккаунта пользователя, контракт `InviteGuardianDto`, HANDOFF §A8), изменить роль/can_pickup, «Отозвать доступ» (destructive-confirm), «Отозвать все QR пользователя» (destructive-confirm с объяснением). *Визуал/лейаут модала — 1:1 по `screens-core.jsx` ChildDetail; меняется только набор полей под фактический контракт.\_
  3. **Группа и история** — текущая группа + таймлайн переводов (из→в, кто, причина, дата). Модал «Перевести»: выбор группы + причина.
  4. **Timeline** — лента событий ребёнка (check-in/out, активности, заметки, фото) — read-only, по датам.
  5. **Платежи** — превью счетов/оплат (мини-таблица + ссылка «Все платежи» в Биллинг с фильтром по ребёнку).
  6. **Диагностика** — превью последних записей (read-only).
  7. **Статус-история** — аудит изменений статуса (previous→new, причина архива, кто, когда), пагинация. Только админ.
  8. **Face ID** — индикатор «зарегистрирован / нет», дата; переход в раздел Face. Метка Phase C.
- **Действия-модалы:**
  - **Архивировать:** destructive-модал, **обязательное** поле «Причина архива» (1–500 символов, счётчик), предупреждение «тарифы закроются, будет инициирован перерасчёт/возврат». После — статус archived, ребёнок приглушён.
  - **Реактивировать:** confirm-модал; после успеха — баннер/тост «Назначьте новый тариф» со ссылкой в Назначения тарифов.
  - **Перевести:** нельзя для архивного (показать понятную ошибку «сначала реактивируйте»).
- **Состояния/edge:** архивный ребёнок — read-only баннер сверху; 404 — «карточка не найдена или нет доступа».

### 6.4 Группы (`/groups`, `/groups/:id`)

- **Список — Layout:** карточки или таблица. На карточку: название, возраст (мес. диапазон), заполненность (активных детей / capacity — прогресс-бар, индикатор переполнения красным), локация, primary-mentor, статус. Кнопка «Создать группу».
- **Создание/редактирование:** название*, вместимость*, возраст min/max (в месяцах — поле с подсказкой «в месяцах»), текущая локация (селект). Валидация: min < max (иначе inline-ошибка).
- **Карточка группы — табы:**
  1. **Обзор** — поля + edit. Кнопка «Деактивировать» (если есть активные дети — модал-блокер «Сначала переведите детей в другие группы», ссылка на список детей группы).
  2. **Менторы** — таблица активных (ФИО, is_primary-метка). Действия: «Назначить ментора» (через раздел Сотрудники), «Сделать основным (primary)», «Снять». Подсказка-инвариант: «У группы ровно один основной ментор; ментор привязан к одной активной группе».
  3. **Дети** — список детей группы (ссылки в карточки).
  4. **История менторов** — таймлайн назначений (кто, с/по, был ли primary).
- **Состояния:** пустой список групп — CTA; переполненная группа — визуальный warning.

- **Форма добавления (модал/страница):** ФИО*, телефон* (E.164), роль* (селект). **Динамические поля:** mentor → выбор группы (опц.); specialist → тип специалиста* (psychologist/speech_therapist/music_teacher/physical_ed/nutritionist — локализованные подписи); admin/reception → без группы и типа. Дата найма. Подсказка: «Сотрудник войдёт в Staff App по своему номеру через SMS-код; приглашение/ссылка не требуются».
- **Карточка сотрудника:** данные + edit (роль, тип, даты найма/увольнения — валидация комбинаций роль×тип). Для mentor — управление назначениями (назначить в группу / сделать primary / снять). Кнопки: «Деактивировать»/«Активировать», «Отозвать все QR». Деактивация — confirm с объяснением (снимется с групп, сессии завершатся).

### 6.10 Биллинг

Общий раздел с подразделами. Денежные суммы — KZT, формат `120 000 ₸`. Везде статус-бейджи по §4.6.

#### 6.10.1 Счета (`/billing/invoices`, `/billing/invoices/:id`)

- **Список:** таблица: ребёнок, тип (monthly/prepayment\_\*/late_pickup_fee/additional_service/other), период, сумма (к оплате / после скидки), статус-бейдж, срок (due_date). Фильтры: статус, тип, ребёнок, due_date. Кнопка «Создать начисление» (разовое: ребёнок, тип, сумма, срок, описание, опц. позиции line items).
- **Карточка счёта:** шапка (сумма, статус) + секции: Позиции (line items: описание, кол-во, цена, итого), Связанные оплаты, Возвраты, Фискальные чеки, Применённые скидки. Действия: «Отметить оплату наличными» (confirm; обработать «уже оплачен»), «Отменить счёт» (destructive-confirm; только pending/partial; обработать конфликт состояния).

#### 6.10.2 Оплаты (`/billing/payments`, `/billing/payments/:id`)

- **Список:** ребёнок, сумма, провайдер, статус, дата. Фильтры: провайдер, статус, ребёнок, диапазон дат.
- **Карточка платежа:** детали + технический `provider_payload` (свернутый JSON-вьюер для саппорта). Read-only.

#### 6.10.3 Тарифные планы (`/billing/tariff-plans`)

- **Список:** название, тип (monthly_base/additional_service/late_pickup/meal_upgrade), сумма, к чему применяется (child/group/age_range), активен, период. Деактивация.
- **Форма:** название*, тип*, сумма*, валюта (KZT), applies_to* (динамически: age_range → min/max месяцев; group → селект группы), **конструктор `discount_rules`** (скидка за братьев/сестёр %, prepay 3/6/12/24 мес %, льготная категория), период действия. Ошибки пересечения периодов — понятное сообщение.

#### 6.10.4 Назначения тарифов (`/billing/tariff-assignments`)

- **Список:** ребёнок, тарифный план, индив. сумма/причина (льгота), период. Фильтры: ребёнок, план, активно на дату.
- **Форма назначения:** ребёнок* (combobox), тарифный план* (только активные), индив. сумма (льгота) + причина, период (valid_from\*, valid_until?). Обработать пересечение назначений по ребёнку. Связь со сценарием реактивации ребёнка («назначьте новый тариф»).

#### 6.10.5 Праздники (`/billing/holidays`)

- **Layout:** календарь/список по году/месяцу. Праздник: дата*, название RU/KK*, флаг «тарифицируется ли день» (is_billable). CRUD. Уникальность по дате — обработать конфликт.

#### 6.10.6 Возвраты (`/billing/refunds`)

- **Список:** ребёнок/платёж, сумма, причина, статус-бейдж (pending/approved/processed/rejected), дата. Фильтры: статус, платёж.
- **Создание:** платёж* (выбор), сумма* (≤ суммы платежа), причина\*.
- **Карточка возврата:** действия по state machine — «Одобрить» (pending→approved), «Отклонить» (с обязательной причиной 1–500), «Провести» (approved→processed). Кнопки доступны соответственно текущему статусу. Контекст: возврат при архивации ребёнка появляется автоматически как pending — подсказать оператору «требует решения».

#### 6.10.7 Скидки (`/billing/discounts`, `/billing/discounts/new|:id`)

- **Список:** название (по локали), тип (% / фикс), статус-бейдж (draft/active/paused/expired/cancelled), период, использовано (used_count / лимиты), приоритет, stackable. Фильтры по статусу/периоду.
- **Конструктор скидки (wizard/одна форма с секциями):**
  1. **Основное:** название RU/KK*, описание RU/KK, тип (percentage/fixed_amount)*, размер\*.
  2. **Условия — визуальный конструктор:** добавление правил из набора типов — Предоплата N месяцев, Кол-во детей в семье, Возраст ребёнка, Льготная категория, Способ оплаты, Раннее платёж (до N числа), Месяц дня рождения, Период дат, Первый платёж; + композиция **И/ИЛИ** (all_of/any_of, вложенность). Каждый тип условия — своя мини-форма.
  3. **Таргетинг:** Все / Группы / Дети / Типы тарифов / Возрастной диапазон (мультиселект соответствующих сущностей).
  4. **Период:** valid_from\*, valid_until.
  5. **Лимиты:** max на ребёнка, общий max.
  6. **Приоритет/стек:** priority (число), stackable (toggle).
  7. **Уведомление:** notify_on_activation (toggle), текст push RU/KK.
- **Действия по state machine:** «Активировать» (draft→active, если есть push — предупредить «уйдёт уведомление родителям»), «Пауза», «Возобновить», «Отменить» (необратимо — destructive-confirm). Редактирование — только в draft.
- **Статистика применения:** таблица применений (ребёнок, счёт, сумма скидки) — служит «превью» («N детей получили скидку»).

#### 6.10.8 Фискальные чеки (`/billing/fiscal-receipts`)

- **Phase A:** только read-only список (фильтры: статус, провайдер, платёж, fiscal_sign). Поля: чек, платёж, провайдер, статус, дата. Подзаголовок-баннер «Расширенные операции (повтор, очередь, отчёты) — в следующей фазе». Экраны retry/queue/report заложить в навигацию как **disabled-заглушки** «Доступно в Phase B».

### 6.14 Face ID (`/face`) — Phase C

- **Назначение/статус:** конфигурация биометрии. Распознавание/обработка видео — следующая фаза. Дизайн делаем, но весь раздел маркируется баннером «Раздел в разработке (Phase C) — данные не обрабатываются».
- **Layout:** табы:
  1. **Согласия (consents):** список (subject: ребёнок/опекун/сотрудник; кем зафиксировано; дата; статус — действует/отозвано). Создать согласие: subject + загрузка скана подписанного согласия (обязательно по закону РК — подчеркнуть в UI). Отзыв согласия (с причиной) — каскадно деактивирует профиль.
  2. **Профили (face-profiles):** список по subject, статус. Enrollment: выбор subject + загрузка видео 5–10 сек + привязка к **активному согласию** (без согласия enrollment запрещён — заблокировать кнопку с объяснением). Действия: пере-enrollment, деактивация, удаление.
  3. **Журнал распознаваний:** события (камера, статус matched/rejected_spoof/..., дата) — read-only.
- **UX-акцент:** строгий порядок «сначала согласие → потом enrollment»; юридическое предупреждение про биометрию.

- **Вкладка «Оплата» (`?tab=payments`) — Kaspi Pay (SMS-онбординг):** готового handoff-дизайна нет (см. OPEN_QUESTIONS §A25) — строится по существующей дизайн-системе вкладок (карточка-статус как в Фискальных/Подписке). Один кассирский аккаунт Kaspi на садик.
  - **Карточка статуса** (по `GET /admin/kaspi/status`):
    - `active` — зелёный бейдж «Подключено», KV-список (телефон кассира, `org_name`, «последняя проверка» `last_checked_at`), кнопки **Переподключить** (запускает мастер заново) и **Отключить** (destructive-confirm).
    - `pending` — нейтральный бейдж «Подключение не завершено», кнопка «Продолжить/Подключить».
    - `expired` — warning-баннер «Переподключите Kaspi — сессия истекла» + кнопка «Переподключить». Баннер также появляется по WS-событию `kaspi.session_expired` (инвалидация статуса + тост).
    - `revoked` / не подключено — пустое состояние «Kaspi не подключён» + кнопка «Подключить Kaspi Pay».
  - **Мастер подключения (3 шага, в модале/секции):**
    1. (скрытый) `connect/init` → `process_id` (вызывается при старте мастера, пользователю не показывается отдельным шагом).
    2. **Телефон кассира** — инпут формата `7XXXXXXXXXX` (11 цифр, без `+`/пробелов; **НЕ E.164** — отдельная маска/валидация от обычного телефона). Кнопка «Отправить код» → `send-phone`.
    3. **SMS-код** — OTP-инпут (как на входе). ⚠️ предупреждение «Код отправлен кассиру по SMS — вводите внимательно» (verify-otp инициирует реальную SMS, попытки беречь). Кнопка «Подтвердить» → `verify-otp` → при `{connected:true}` мастер закрывается, карточка статуса обновляется на `active`.
  - **Ошибки** (через error-map): `kaspi_already_connected`, `kaspi_app_version_outdated` (подсказать обратиться к суперадмину), `kaspi_unknown_process` (TTL ~5 мин истёк — начать заново), `kaspi_otp_invalid` (на шаге 3, `setError` на OTP), `kaspi_finish_failed`.

## 7. Сквозные паттерны (спроектировать один раз, переиспользовать)

- **OTP-инпут** — 6 ячеек, авто-переход, вставка из буфера, таймер ресенда, состояние ошибки/блокировки. Используется: вход (обязательно). (Подтверждения изменения прав опекунов через OTP — в Parent App, не в админке.)
- **Destructive-confirm с причиной** — модал с заголовком-предупреждением, текстовым полем «Причина» (счётчик символов, лимит), кнопкой danger. Используется: архив ребёнка, отклонение возврата, отмена скидки, отзыв доступа/QR, отмена счёта.
- **Combobox-поиск сущности** — выбор ребёнка/группы/сотрудника/тарифа по названию (debounce, аватар/доп.инфо в опции).
- **Парное RU/KK-поле** — для всех двуязычных вводимых данных (название блюда, заголовок/текст контента, название праздника/скидки, тексты push). Две вкладки языка или два инпута рядом; индикатор незаполненного языка.
- **Период (from/to) пикер** — единый компонент для фильтров и форм (с пресетами: сегодня/неделя/месяц).
- **State-machine-кнопки** — набор действий, где недопустимые переходы задизейблены с тултипом-причиной (счета, возвраты, скидки, заявки, лиды).
- **JSON-вьюер** (свёрнутый) — для технических payload (платёж, DLQ-задача) — для саппорт-сценариев.
- **Пустые состояния** — у каждого списка своя иллюстрация + поясняющий текст + CTA; отдельно «ничего не найдено по фильтрам».
- **Таблица** — единый компонент с offset- и cursor-режимами пагинации.

## 8. Локализация, доступность, форматирование

- **RU + KK** полностью (UI + валидационные сообщения + статусы человеко-читаемо). Шрифт обязан поддерживать казахскую кириллицу. Двуязычные данные — парные поля.

- **Тон сообщений:** дружелюбный, без техжаргона и кодов ошибок; для необратимых действий — чёткое предупреждение о последствиях.

## 10. Mobile-адаптация (<1024px)

### 10.1 Цель и контекст

Mobile-адаптация существующих экранов Admin Web. Не отдельный продукт и не PWA — то же веб-приложение, которое корректно работает со смартфона. Основная аудитория по-прежнему desktop (ежедневная CRM-работа в кабинете), но администратор может проверить дашборд, принять заявку родителя, посмотреть посещаемость или отметить оплату со смартфона (вне кабинета, на ходу, в выходной).

Для родителей и сотрудников существуют **отдельные нативные приложения** — mobile-shell Admin Web не заменяет их.

### 10.2 Брейкпоинт и стратегия

**Брейкпоинт** (resolved, см. OPEN_QUESTIONS M1/M2):

- `< 1024px` — mobile shell (bottom tab bar, mobile top bar, card-based lists)
- `>= 1024px` — desktop shell (sidebar, topbar, table-based lists)

Tablet (768-1023px) использует mobile shell: touch-friendly UI важнее data density в этом диапазоне.

### 10.3 Mobile shell

В отличие от desktop shell (sidebar + topbar + content area), mobile shell состоит из:

- **Top bar** (`.m-bar`): back-кнопка / title / subtitle / action-кнопки. Высота 96px с safe-area padding (56px top для status bar / dynamic island). Вариант `.flat` — прозрачный фон (для detail-экранов с profile header).
- **Scrollable content area** (`.m-scroll`): основной контент с padding 16px, bottom padding 110px (room для tab bar + home indicator). Вариант `.no-bar` — уменьшенный верхний padding.
- **Bottom tab bar** (`.m-tabbar`): floating pill-bar с backdrop-blur, border-radius 22px, shadow, position absolute bottom 22px. 5 primary tabs. z-index: 5.
- **FAB** (`.m-fab`): плавающая кнопка создания, bottom 96px right 18px, 56x56, primary-цвет. Присутствует на экранах со списками (Children, Staff, Invoices, Content и др.).

**Canvas:** iPhone Pro Max, 402x874 (design artboard).
